# Cloudflare test deployment: runbook for the maintainer (provider-validation slice 06)

**PREPARED, NOT EXECUTED.** Nothing here has been run. **Every step below that touches Cloudflare is an external action and needs your explicit confirmation at that step.** Approving this runbook does not authorize any of them.

- **Stop points:** the builder's work stops at step 1. Steps 1–14 are yours or, if you explicitly delegate a step, the delegate's.
- **What the steps build:** the Worker from slice 05 on `workers.dev`, behind Cloudflare Access, with one R2 bucket and one D1 database, for **synthetic data only**, with a **$5/month** ceiling.
- **Coverage and sources:** `coverage.md` (each step's source is cited there).

**Conventions:**

- `<run>` is `<yyyymmdd>-<runid>`, for example `20260927-a1`. The bucket is `rp-packets-test-<run>`, the database `rp-aliases-test-<run>`, and the Worker `rp-publisher-test`.
- **Evidence:** capture what each step lists, and nothing secret. Never capture the service token's Client Secret, the API token, or a JWT.

## Evidence capture (V2.1: no credential reaches the evidence)

The live fire's evidence held live Access session cookies (F-LF-1), its receipts were never read, and its absence listings could not show their scope. Every live run now uses:

1. **`scripts/cf-capture.mjs` for every HTTP matrix cell,** instead of `curl -si`. It records the request and the response, and strips `set-cookie`, `cookie`, `authorization`, every `cf-access-*` header and an Access login redirect's query at the source. With `--service-token-env RP_CF_TEST` it sends the service token and records it stripped. Each capture runs the secret gate over what it wrote.
2. **`scripts/cf-receipts.mjs` during the run,** after every publish and promote: `node scripts/cf-receipts.mjs --endpoint https://rp-publisher-test.<sub>.workers.dev --out <evidence> --ids-from <the publisher's output> --live` (without `--live` it is a dry run that only shows the requests). Each receipt is read back through the Worker (`GET /_admin/receipts/<id>.json`, service token), checked as `receipt/v2` and secret-free, and saved.
3. **`scripts/secret-gate.mjs` before any packet is built:** a packet is built from evidence only with `node scripts/evidence-packet.mjs --report <report.json> --out <dir> --evidence <evidence>`, which runs the gate (with its planted-sample self-check) over every root and builds nothing unless all are clean.
4. **`scripts/cf-absence.mjs` at teardown** (teardown step 1).

## Scope proof (makes `sufficiencyForApply` evidence)

The generated table says which scopes the deploy token has; this procedure proves the token that ran had exactly those, and that they were enough.

1. **After step 3:** `node scripts/cf-token-verify.mjs --account <account_id> --live` (from the repo root). It must report `"state": "active"` and an expiry within the 1-day TTL. Capture its output: the token's ID, status and expiry, never the token.
2. **With it:** the dashboard summary of `rp-deploy-<run>`, checked row by row against the generated table (step 3's evidence). The API cannot read a token's permissions with the granted scopes, so this capture is the permission record.
3. **Sufficiency:** step 6's successful `tofu apply`, run with exactly those scopes, is the evidence that they suffice for apply. Record it in the live-run evidence; after the run, the canonical list's `sufficiencyForApply` changes from NOT_EXECUTED to verified, citing that evidence, in a reviewed change.
4. **The unverified scope (keep or drop):** before step 12's apply, edit `rp-deploy-<run>` in the dashboard to remove the one scope the generated table marks *unverified*, re-run step 1 of this procedure, then run step 12's `tofu plan` and `tofu apply`.
   - **If both succeed,** that scope is not needed for apply: the canonical list drops it after the run (a reviewed change), with this run as the evidence.
   - **If either fails with an authorization error,** record the error, add the scope back, and re-run step 12: the canonical list marks it verified, citing the error.
   - Either way the token is revoked in step 13 as usual.

## Safety notes

- **One owner per resource.** Terraform owns the bucket, the database, the Worker and its route, and (V2.1) the Access application and its policies. Only the service token is dashboard-owned, so its secret never enters state. Never `wrangler deploy` this Worker. Wrangler is not used at all (V2.1): the schema goes through `scripts/d1-schema.mjs`, and `infra/cloudflare/wrangler` only keeps a byte-identical copy of the schema as its migration file.
- **The Worker fails closed.** Without its Access configuration it refuses every request. It has no delete route, and its only outbound request fetches its own team's Access signing keys.
- **No step here creates a custom domain, DNS record, route, public bucket or bucket lock.**
